08 — How to Search

Debug and search
like a pro

The most important skill in Linux isn't memorising commands — it's knowing how to find answers. Reading errors, using man pages, mining logs, and Googling effectively.

01

Read Error Messages

Most people skip the error message

The error message almost always tells you exactly what went wrong and where. Read it completely — even if it looks scary — before Googling. 80% of the time the solution is right there.

Anatomy of a Common Error

Job for syncthing@dell.service failed because the control process exited with error code.
See "systemctl status syncthing@dell.service" and "journalctl -xe" for details.
→what failedsyncthing@dell.service — tells you which service to investigate
→why"control process exited with error code" — it crashed on startup
→next stepsIt literally tells you the commands to run next! Run both of them.

Common Error Patterns and What They Mean

Line Numbers Are Your Friends

errors with line numbers
bash -n script.sh # syntax check without running bash -x script.sh # trace: shows each line + command as it runs bash -x script.sh 2>&1 | head -30 # first 30 lines of trace
02

Man Pages — Built-in Docs

Man pages are the first place to look, not the last. They're built-in, always accurate for your version, work offline, and show you every flag a command has.

using man pages effectively
man ssh # SSH man page man 5 sshd_config # config file format (section 5) man -k "disk usage" # search all man pages man curl | grep -A2 "\-o" # find specific flag in man page
# Navigation inside man: /search → n next → G end → q quit

Better Alternatives to man

quick help tools
# tldr — practical examples (more beginner-friendly than man) sudo apt install tldr tldr ssh # common use cases with examples tldr tar
# Every command has --help ssh --help systemctl --help
# type — what exactly IS this command? type ls # "ls is aliased to 'ls --color'" type cd # "cd is a shell builtin"
03

Reading Logs

When something breaks, the logs almost always have the answer. The question is knowing which log to check.

Log file / commandWhat it contains
journalctl -xeRecent systemd log + explanations. First place to look.
journalctl -u serviceAll logs for one specific service
/var/log/auth.logAll authentication: SSH logins, sudo, su
/var/log/syslogGeneral system messages
/var/log/kern.logKernel messages (driver errors, hardware)
/var/log/apt/history.logPackage install/remove history
dmesgKernel ring buffer — hardware events, USB, disk
/var/log/fail2ban.logFail2Ban bans and unbans

Essential Log Commands

log investigation
# Follow live logs tail -f /var/log/syslog journalctl -f journalctl -u syncthing@dell -f
# Search logs grep -i "failed" /var/log/auth.log | tail -20 journalctl -u ssh | grep "Failed password"
# Filter by time journalctl --since "1 hour ago" journalctl -b -1 # previous boot (great for crash analysis)
# Filter by priority journalctl -p err # only errors and above
04

Googling Like a Pro

The key insight

Google the specific error message (not a description of your problem). Copy the exact error text, remove parts that are specific to your machine (usernames, IPs, timestamps), and search that. Someone has had this exact error before.

Don't Google This — Just Run These

self-answering commands
# "why did this service fail?" systemctl status service-name journalctl -u service-name -n 50
# "which process is using port X?" ss -tulpn | grep :PORT
# "why is disk full?" du -sh /* 2>/dev/null | sort -h | tail -20
# "is the network ok?" ping -c4 8.8.8.8 curl -I https://google.com
05

strace — X-Ray Vision

What strace does

strace prints every system call a process makes — every file it opens, every network connection it tries, every permission check. When a program silently fails and you have no idea why, strace shows you exactly what it was trying to do at the moment it failed.

strace
strace ls # trace ls — watch every syscall strace -p 1234 # attach to running process by PID strace -e openat ls # only file-open calls strace -c ls # count + time per syscall type strace ls 2>&1 | grep ENOENT # find "no such file" errors strace -f bash script.sh # trace script + child processes
06

Asking Good Questions

When you need help (on forums, from AI, or from friends), how you ask determines how good the answer is.

✅
Good question template: "I'm trying to do X on Ubuntu 24.04. I expected Y to happen. Instead, I got [paste exact error]. I've already tried A and B. Here's the relevant config: [paste it]."
❌
Bad question: "Syncthing doesn't work, please help." — No OS, no error, no context. Impossible to help with.

The XY Problem

The most common bad question pattern: You have problem X. You think Y will solve it. You ask about Y without mentioning X. People answer about Y, which wasn't the real issue. Always explain what you're ultimately trying to achieve, not just what you think the solution is.

Always Include This

IncludeHow to get it
OS and versionlsb_release -a

Service status/logssystemctl status svc, journalctl -u svc -n 30
07

Debug Checklist

When something breaks and you don't know where to start, run through this list in order:

1
Read the exact error message

The whole thing. Don't skim. What file? What line? What permission? What was it trying to do?

2
Check service status and recent logs
bash
systemctl status service-name journalctl -u service-name -n 50 --no-pager
3
Check permissions

ls -la /path/to/file — Does your user own it? Is it executable if it should be?

4
Check if port/network is the issue

ss -tulpn | grep :PORT — Is the service even listening? ping server — Is the host reachable?

5
Check disk and memory

df -h — Is disk full? free -h — Is RAM exhausted?

6
Check what changed recently

journalctl --since "1 hour ago" — Did something fail right before? Did you edit a config?

7
Google the exact error

Add your distro name + version. Check the Arch Wiki even on Ubuntu — it's that good.

8
Use strace if all else fails

strace command 2>&1 | grep -E "ENOENT|EACCES|ECONNREFUSED" — watch what the program actually does at the OS level.
