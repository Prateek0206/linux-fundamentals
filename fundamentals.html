What Is Linux?

The one-sentence answer

Linux is a kernel — the program that sits between your hardware and your software and manages everything. "Ubuntu", "Arch", "Fedora" are distributions (distros): they bundle the Linux kernel with software, a package manager, and tools to make it usable.

When people say "I use Linux", they really mean "I use a Linux-based operating system". The Linux kernel itself was written by Linus Torvalds in 1991 and is still actively developed today by thousands of contributors worldwide.

💡
Kernel space vs User space: Programs you run (Syncthing, SSH, bash) live in user space. The kernel lives in kernel space. User programs can't directly access hardware — they have to ask the kernel via system calls. This is a fundamental security boundary.
02

The Kernel

The kernel has five main jobs it does constantly:

⚙️
Process Management
Creates, schedules, and kills processes. Decides which process runs on which CPU core at any given moment.
🧠
Memory Management
Gives each process its own virtual memory space. Manages physical RAM and swap. Prevents processes from accessing each other's memory.
💾
Filesystem
Translates file operations (open, read, write) into actual disk I/O. Manages inodes, directories, and permissions.
🌐
Network Stack
Handles TCP/IP, UDP, sending and receiving packets, routing. All your SSH and Syncthing traffic goes through here.
🔌
Device Drivers
Speaks to hardware (network card, disk, USB). A driver is code inside the kernel that knows how to talk to a specific device.

System Calls — How Programs Talk to the Kernel

When your Telegram bot script runs curl to send a request, here's what actually happens under the hood:

what happens when curl runs
1. curl starts → kernel creates a process (fork/exec syscall)
2. curl calls socket() → kernel creates a network socket
3. curl calls connect() → kernel initiates TCP connection
4. curl calls write() → kernel sends data over the socket
5. curl calls read() → kernel waits for response, puts in buffer
6. curl calls write(STDOUT) → kernel writes to terminal
7. curl calls exit() → kernel cleans up, frees memory

You can watch these syscalls in real time with strace: strace curl https://api.telegram.org — it prints every kernel call. This is incredibly useful for debugging.

GRUB — The Bootloader

GRUB (Grand Unified Bootloader) is what shows the boot menu if you have multiple kernels or OS installed. Its config lives at /etc/grub/grub.cfg (auto-generated) and /etc/default/grub (where you edit settings). After editing: sudo update-grub.

systemd — PID 1

The first process the kernel starts is PID 1 — on Ubuntu, this is systemd. It's the parent of all other processes. If PID 1 dies, the system panics. systemd reads its unit files from /etc/systemd/system/ and /lib/systemd/system/ and starts services in parallel (much faster than the old sequential SysV init).

boot analysis
systemd-analyze # Total boot time systemd-analyze blame # Which services took longest systemd-analyze critical-chain # What was the bottleneck

Filesystem Hierarchy

Everything is a file

In Linux, almost everything is represented as a file. Your keyboard is a file (/dev/input/event0). Network interfaces are files. The CPU's temperature is a file (/sys/class/thermal/thermal_zone0/temp). Even running processes are files in /proc/. This "everything is a file" philosophy means you can use the same tools (cat, echo, grep) on almost anything.

Inodes — What Files Really Are

Every file on Linux is represented by an inode — a data structure that stores: file size, permissions, owner, timestamps, and pointers to where the actual data is on disk. The filename is just a label that points to an inode. This is why mv is instant (it just changes the label), and why hard links work (two names can point to the same inode).

inodes
ls -i file.txt # Show inode number stat file.txt # Full inode info: size, perms, timestamps df -i # Inode usage (can run out before disk is full!) find / -inum 123456 # Find file by inode number

Processes

A process is a running instance of a program. When you run ls, the kernel creates a process, runs the ls program in it, and then destroys the process when it finishes. Every process has a unique PID (Process ID).

Process States

StateCodeWhat it means
RunningRCurrently using the CPU
SleepingSWaiting for something (I/O, timer, event)
Disk SleepDUninterruptible sleep — waiting for disk I/O
StoppedTPaused (Ctrl+Z)
ZombieZFinished but parent hasn't read exit code yet
process commands
ps aux # All running processes ps aux | grep syncthing # Find a specific process pgrep syncthing # Just get the PID pstree # Process tree — who spawned what htop # Interactive monitor kill 1234 # Graceful terminate (SIGTERM) kill -9 1234 # Force kill (SIGKILL) — no cleanup pkill syncthing # Kill by name nohup command & # Run in background, keep after logout jobs # List background jobs in current shell bg %1 # Resume job 1 in background fg %1 # Bring job 1 to foreground

Signals

Signals are notifications sent to a process by the kernel or another process. When you press Ctrl+C, your terminal sends SIGINT to the foreground process. Programs can choose to handle most signals, but SIGKILL and SIGSTOP cannot be caught or ignored.

SignalNumberShortcutMeaningCan ignore?
SIGTERM15—Graceful shutdown request. Default for kill.Yes
SIGKILL9—Force kill immediately. No cleanup possible.No
SIGHUP1—"Hangup" — reload config for many daemons (nginx, sshd)Yes
SIGINT2Ctrl+CInterrupt — politely cancelYes
SIGQUIT3Ctrl+\Quit + dump coreYes
SIGSTOP19Ctrl+ZPause process. Cannot be caught.No
SIGCONT18—Resume a stopped processYes
SIGUSR1/210,12—User-defined — app decides what to doYes
⚠️
Always try SIGTERM before SIGKILL. kill -9 (SIGKILL) prevents the process from cleaning up — open files may stay locked, databases may corrupt. Use it only when SIGTERM doesn't work.

The Shell

The shell is just a program — it reads what you type, interprets it, and runs commands. When you SSH into your Dell server, you get a bash shell. Bash is by far the most common on Linux servers.

What happens when you type a command

When you type ls -la /home: bash splits it into tokens (ls, -la, /home). It looks for ls in directories listed in the $PATH environment variable. It calls fork() to create a child process and exec() to replace it with the ls program. ls runs, prints output, exits. Bash waits for it to finish (or doesn't, if you added &), then shows your prompt again.

Important Shell Concepts

shell internals
echo $PATH # Where bash looks for programs which ls # Full path to a command type ls # Is it a file, alias, or builtin? echo $SHELL # Your current shell echo $$ # PID of current shell echo $? # Exit code of last command (0=success) env # All environment variables export MYVAR=hello # Set env variable (available to child processes) alias ll="ls -la" # Create a shortcut history # Command history !! # Repeat last command !grep # Repeat last command starting with 'grep'

File Descriptors

Everything is a file — including input and output

Every process gets three standard "files" connected to it at birth: stdin (input, FD 0), stdout (output, FD 1), and stderr (error output, FD 2). When you run a command in the terminal, stdin is your keyboard, stdout is your screen, and stderr is also your screen (but separate so you can redirect them independently).

redirection
command > file.txt # stdout to file (overwrites) command >> file.txt # stdout to file (appends) command 2> errors.txt # stderr to file command 2>&1 # stderr → stdout (merge them) command > /dev/null 2>&1 # Discard ALL output (silence a cron job) command < input.txt # Feed file as stdin command &> all-output.txt # Both stdout and stderr to file

Pipes & Redirection

A pipe | connects the stdout of one command to the stdin of the next. This is the Unix philosophy in action: small tools that do one thing well, chained together to do complex things.

real pipe examples
ps aux | grep syncthing # Find process cat /var/log/auth.log | grep "Failed" | wc -l # Count failed logins ls -la | sort -k5 -n | tail -10 # 10 biggest files # Find which IPs successfully logged in via SSH, sorted by frequency: journalctl -u ssh | grep "Accepted" | awk '{print $11}' | sort | uniq -c | sort -rn

Permissions Deep Dive

Linux permissions are built around three entities: owner, group, and others. Each gets three bits: read (4), write (2), execute (1).

permission bits explained
-rwxr-xr-- 1 dell dell 4096 Jan 1 script.sh

│└─┬─┘└─┬─┘└─┬─┘
│ │ │ └── others: r-- = 4 (read only)
│ │ └─────── group: r-x = 5 (read + exec)
│ └──────────── owner: rwx = 7 (full access)
└─────────────── - = file, d = dir, l = symlink

Binary: rwx = 111 = 7 | rw- = 110 = 6 | r-x = 101 = 5 | r-- = 100 = 4

Common Permission Patterns

700rwx------Private scripts/directories

Special Bits: SUID, SGID, Sticky

BitOn filesOn directoriesSet with
SUID (4000)Run as file's owner (e.g. passwd runs as root)—chmod u+s file
SGID (2000)Run as file's groupNew files inherit directory's groupchmod g+s dir
Sticky (1000)—Only owner can delete their files (used on /tmp)chmod +t dir

ACLs — Beyond Basic Permissions

When owner/group/others isn't granular enough, use Access Control Lists:

ACLs
getfacl file.txt # Show ACL setfacl -m u:alice:rw file.txt # Give alice read+write setfacl -m g:devs:rx /srv/ # Give group devs read+exec on dir setfacl -x u:alice file.txt # Remove alice's entry setfacl -b file.txt # Remove ALL ACLs

Man Pages

The manual pages (man) are the authoritative documentation for every command on your system. They're built-in, always accurate for your version, and available offline. Learning to read them efficiently is a superpower.

man page navigation
man ls # Open ls man page man 5 passwd # Section 5 = file formats (not the command) man -k keyword # Search all man pages (like apropos) man -f ls # One-line description # Inside man: /search ← search | n ← next | q ← quit | G ← end | g ← start
SectionContent
1User commands (ls, cat, ssh)
2System calls (open, fork, write)
3C library functions
4Device files (/dev/*)
5File formats (fstab, passwd, hosts)
6Games
7Miscellaneous (protocols, standards)
8Admin commands (systemctl, mount, fdisk)
💡
Use tldr ls (install: sudo apt install tldr) for practical examples instead of full man pages. It shows the most common uses of any command in a quick cheat format. Great companion to man pages.
